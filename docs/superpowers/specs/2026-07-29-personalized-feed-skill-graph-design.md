# 개인화 공고 피드와 로컬 탐색형 스킬맵 설계

## 목표

사용자가 `C++` 같은 보유 기술을 등록하면 메인 피드의 공고 순서가 실제로 달라지고,
각 공고가 추천된 이유를 바로 이해할 수 있어야 한다. 스킬맵은 관계를 구경하는 화면이 아니라
현재 기술에서 다음 기술과 관련 공고로 이동하는 탐색 도구가 되어야 한다.

이번 변경은 다음 두 결과를 함께 만든다.

1. 첫 화면부터 무한 스크롤 끝까지 동일한 개인화 규칙을 적용한다.
2. 스킬맵을 선택 기술 중심의 로컬 그래프로 바꾸되 기존 Canvas 성능 기반을 유지한다.

## 디자인 맥락

- 대상: 자신의 기술로 지원할 공고와 다음 학습 방향을 빠르게 정하려는 국내 개발자
- 핵심 행동: 맞춤 공고를 열거나, 근거를 확인한 뒤 다음 기술을 학습 목록에 추가하기
- 톤: 기술적이고 절제된 데이터 중심 `modern-minimal`
- 보존 항목: `design.md`의 보라색 브랜드, Pretendard, Workbench/Map 구조, 4px 간격,
  44px 터치 기준, 제한된 상태 애니메이션

## 확인된 문제

### 메인 공고가 실제로 개인화되지 않음

홈 모델에는 공고 적합도 점수 함수가 있지만, 점수 입력으로 쓰는 스킬 그래프 요청은
`include_evidence=false`가 기본값이라 `evidence`가 비어 있다. 모든 공고 점수가 `null`이 되어
등록 기술과 상관없이 최신 공고 순서가 유지된다.

2026-07-29 운영 데이터에서 `C++`은 265개 공개 공고에 등장했지만, `C++`을 등록한 홈의
첫 추천 공고는 C++ 요건이 없는 SRE 공고였다. 이는 개인화 문구만 보이고 실제 피드는 바뀌지
않는 신뢰 문제다.

### 홈이 불필요하게 무거운 그래프 요청에 의존함

홈은 공고 정렬을 위해 약 115KB의 스킬 그래프 응답을 함께 요청하지만 실제 근거는 비어 있다.
또한 `owned_skills`가 그래프 URL에 포함되면 응답이 `private, no-store`가 되어 같은 C++ 관계망도
사용자마다 다시 계산한다. 운영 측정값은 개인 기술이 포함된 요청이 약 0.96~1.00초였고,
동일한 공개 관계망의 warm-cache 요청은 약 0.08~0.10초였다.

### 스킬맵의 의미와 행동이 분산됨

현재 Canvas, 동적 import, 모바일 노드 제한, 화면 이탈 시 정지 등 성능 기반은 적절하다.
다만 다음 문제가 남아 있다.

- 노드가 대부분 같은 회색이라 분야 군집을 빠르게 읽기 어렵다.
- 추천 기술 다수가 모두 점선 테두리로 표시돼 강조가 강조로 보이지 않는다.
- 왼쪽 제어, 중앙 그래프, 오른쪽 분석, 하단 추천이 서로 경쟁한다.
- 모바일에서 페이지 스크롤과 그래프 이동의 경계가 명확하지 않다.
- 그래프 선택이 다음 학습이나 공고 확인으로 자연스럽게 이어지지 않는다.

## 설계 원칙

- 개인화는 문구가 아니라 데이터 조회와 정렬 단계에서 적용한다.
- 추천 이유를 숨은 점수로만 두지 않고 카드에서 설명한다.
- 사용자를 같은 기술 안에 가두지 않도록 공고 슬롯의 20%는 탐색용으로 남긴다.
- 그래프 색·크기·선은 각각 하나의 의미만 갖는다.
- 전체 관계망보다 현재 기술 주변의 결정 가능한 관계를 먼저 보여준다.
- 저사양 기기에서 더 많은 노드를 그리는 것보다 빠른 선택과 근거 확인을 우선한다.
- 기존 보라색, Pretendard, 4px 간격, 44px 터치 기준과 자연스러운 한국어를 유지한다.

## 1. 개인화 공고 피드

### API 계약

기존 `GET /api/postings`에 반복 가능한 `owned_skills` 쿼리를 추가한다.

```text
GET /api/postings?owned_skills=C%2B%2B&owned_skills=Python&limit=20&offset=0
```

- 기술은 서버에서 기존 스킬 카탈로그 규칙으로 canonicalize한다.
- 공백과 중복을 제거하고 최대 20개만 허용한다.
- `owned_skills`가 없으면 기존 최신·기업 다양성 정렬을 그대로 사용한다.
- `owned_skills`가 있으면 개인화 응답이므로 공개 CDN 캐시를 사용하지 않는다.
- 응답 스키마는 기존 `PostingListResponse`를 유지한다.

별도 추천 전용 응답 타입을 만들지 않는다. 공고 요약에 이미 필수, 우대, 분류되지 않은 기술이
포함돼 있으므로 클라이언트가 같은 사실에서 추천 이유를 계산할 수 있다.

### 맞춤 공고 점수

한 개 이상의 보유 기술이 확인된 공고만 맞춤 스트림에 들어간다. 정렬은 다음 값을
사전식 우선순위로 비교한다.

1. 일치한 필수 기술 수
2. 필수 기술 충족률 (`일치 필수 / 전체 필수`)
3. 일치한 우대 기술 수
4. 일치한 분류되지 않은 기술 수
5. 전체 일치 기술 수
6. 최초 수집 시각, 마지막 확인 시각, 공고 ID

필수 요건이 없는 공고의 필수 충족률은 0으로 계산한다. 단순 키워드 검색이 아니라
신뢰도 기준을 통과한 `PostingSkill`의 canonical skill과 requirement type만 사용한다.

같은 회사 공고가 연속으로 화면을 점유하지 않도록 회사별 순번을 계산하고, 한 라운드에서
회사당 최대 2개만 먼저 노출한다. 그 뒤 각 회사의 다음 공고가 다음 라운드에 참여한다.

### 80/20 혼합 규칙

공고 슬롯 기준으로 다음 패턴을 반복한다.

```text
맞춤 · 맞춤 · 맞춤 · 맞춤 · 탐색
```

- 탐색 스트림은 보유 기술과 일치하지 않는 공개 공고를 기존 최신·기업 다양성 순서로 정렬한다.
- 한 스트림이 부족하면 다른 스트림이 빈 슬롯을 채운다.
- 서버는 전체 스트림의 안정적인 순서를 먼저 정의한 뒤 `offset`과 `limit`을 적용한다.
- 같은 공고는 맞춤과 탐색 스트림에 동시에 들어가지 않는다.
- 페이지 경계가 달라져도 중복·누락이 없어야 한다.

커뮤니티 글과 시장 콘텐츠는 기존 `interleaveHomeSources` 규칙으로 섞는다. 80/20은 전체 피드가
아니라 공고 슬롯에만 적용하므로 커뮤니티 노출량과 무한 스크롤 동작은 바뀌지 않는다.

### SSR과 무한 스크롤의 일관성

- 홈 서버 렌더링의 첫 공고 요청에 `owned_skills`를 전달한다.
- `/api/home-feed/postings`도 같은 기술 목록을 검증해 백엔드에 전달한다.
- 무한 스크롤 요청도 첫 페이지와 동일한 정렬 규칙과 offset을 사용한다.
- 기술 목록이나 경력 조건이 바뀌면 기존 요청을 중단하고 새 피드 세대를 시작한다.
- 개인화 요청의 웹 라우트 응답은 `private, no-store`, 일반 요청은 기존 공개 캐시를 유지한다.

### 공고 카드의 추천 근거

카드 기술 요건에 `unspecifiedSkills`와 `matchedUnspecifiedSkills`를 포함한다.
추천 근거는 우선순위가 가장 높은 실제 일치 항목 하나로 만든다.

- 필수 일치: `C++ 필수 요건 일치`
- 우대 일치: `C++ 우대 요건 일치`
- 분류되지 않은 기술 일치: `C++ 기술 포함`
- 여러 기술 일치: `내 기술 3개 일치`

필수 충족률은 기존처럼 `필수 1/3 일치`로 함께 표시할 수 있다. 탐색 공고에는 거짓 추천
근거를 붙이지 않고 `새로운 분야 탐색`이라는 조용한 메타만 표시한다.

## 2. 로컬 탐색형 스킬맵

Obsidian Graph view의 전체/로컬 그래프, 그룹 색상, 노드 크기, 연결 강조 원리를 참고하되
채용 의사결정에 맞게 단순화한다. 목표는 그래프 자체를 오래 조작하게 하는 것이 아니라
`현재 기술 → 가까운 기술 → 배울 기술 또는 관련 공고`의 흐름을 만드는 것이다.

### 정보 구조

데스크톱은 다음 구조를 사용한다.

```text
짧은 제목·설명
검색 · 시장 핵심/선택 주변/전체 기술 · 필터 버튼
┌──────────────────────────────┬──────────────────┐
│                              │ 선택 기술         │
│        넓은 관계 그래프       │ 수요·분야·상태    │
│                              │ 함께 요구되는 기술│
│                              │ 관련 공고 보기    │
└──────────────────────────────┴──────────────────┘
다음에 배울 기술 · 공고 근거
```

- 기존 왼쪽 제어 열은 그래프 안의 `필터` 패널로 접는다.
- 그래프를 주인공으로 두고 선택 기술 패널은 약 20rem 폭으로 제한한다.
- 빠른 기술 칩은 검색 결과와 현재 보이는 핵심 기술 목록으로 통합해 중복을 줄인다.
- 선택 기술 패널에는 하나의 다음 행동만 강조한다: `관련 공고 보기` 또는 `내 기술에 추가`.

모바일은 제목, 검색, 그래프, 선택 기술, 근거 순서의 단일 열이다. 필터는 접힌 패널로 두고
그래프 높이는 25rem~34rem 범위를 유지한다.

### 그래프 범위

- `시장 핵심`: 전체 시장 수요 상위 기술을 성긴 그래프로 표시한다.
- `선택 주변`: 선택 기술과 직접 연결된 강한 관계를 기본으로 표시한다.
- `한 단계 더 보기`: 직접 이웃의 강한 이웃까지 포함하는 2단계 관계망을 요청한다.
- `전체 기술`: 현재 API 한도 안의 넓은 범위를 보여주는 보조 모드다.
- 노드를 선택하면 해당 기술을 중심으로 관계망을 다시 요청하고 URL의 `seed`를 갱신한다.

그래프 API에 `depth=1|2`를 추가한다. 기본값은 1이다. 2단계에서도 전체 노드 한도는 30,
클라이언트 기본 렌더링 한도는 데스크톱 12개/18개 선, 모바일 8개/10개 선을 넘지 않는다.

- depth 1: 중심 기술과 직접 연결된 기술을 관계 점수 순으로 한도까지 선택한다.
- depth 2: 중심 기술을 제외한 자리의 60%를 강한 직접 이웃에 먼저 배정하고, 나머지를
  그 이웃들과 강하게 연결된 아직 보이지 않는 기술로 채운다.
- 2단계 후보가 부족하면 남은 자리를 직접 이웃으로 채운다.
- 같은 입력에서는 노드 ID와 관계 점수로 최종 tie-break해 결과를 고정한다.

### 시각 언어

- 크기: `log1p(언급 공고 수)`를 사용한 시장 수요
- 채움색: 대표 기술 분야
- 보라색 실선 테두리: 내 기술
- 작은 호박색 점: 다음 학습 추천 상위 3개
- 선 농도: 함께 요구된 공고 수를 정규화한 관계 강도
- 선택·hover: 관계가 있는 노드와 선만 남기고 나머지는 낮은 투명도로 처리

분야 색은 기존 도메인 팔레트를 사용하되 Canvas에서 불투명도를 낮춰 면적 대비를 줄인다.
모든 색의 뜻을 한 줄 범례에 표시한다. 추천 상위 10개를 모두 점선으로 표시하지 않는다.
선은 기본 상태에서 얇게 유지하고 선택 상태에서만 최대 굵기를 높인다.

### 선택 기술 패널

패널은 다음 정보를 순서대로 보여준다.

1. 기술명, 분야, `내 기술` 또는 `추천 기술` 상태
2. 언급 공고, 필수, 우대, 직접 연결 수
3. 함께 요구되는 기술 상위 6개와 실제 동시 등장 공고 수
4. `관련 공고 보기`
5. 해당 기술을 보유하지 않았다면 `내 기술에 추가`

추천 기술인 경우 `왜 추천했나요?` 문장은 실제 fit 분석의 필수·우대·근거 공고 수로 만든다.
근거가 없으면 추천 상태를 표시하지 않는다.

### 모바일 조작

모바일 Canvas는 기본적으로 `스크롤 모드`다. 한 손 드래그는 페이지를 스크롤하고 노드는
탭으로 선택한다. `그래프 조작` 버튼을 켜면 다음 동작을 활성화한다.

- 한 손 드래그: 그래프 이동
- 두 손가락: 확대·축소
- 탭: 노드 선택

조작 모드가 켜졌다는 상태를 버튼과 안내 문구로 명확히 표시하고, 그래프 밖으로 나가거나
모드를 끄면 즉시 페이지 스크롤을 복원한다. 모든 버튼은 최소 44×44 CSS px다.

### 성능

- 그래프 관계망 요청에서 `owned_skills`를 제거한다.
- 보유 여부는 이미 받은 공개 노드 위에 클라이언트 상태로 합성한다.
- 관계망 캐시는 `seed + depth + career_type`으로 공유한다.
- `force-graph` 동적 import, 화면 이탈 시 정지, ResizeObserver rAF 병합을 유지한다.
- Canvas에는 현재 보기 한도의 노드와 선만 전달한다.
- 추천·선택·hover 스타일 변경은 그래프 데이터를 재생성하지 않고 redraw만 요청한다.
- 저사양 환경에서도 무의미한 지속 애니메이션을 실행하지 않으며 reduced motion을 보존한다.

홈에서는 스킬 그래프 요청을 완전히 제거한다. 개인화 정렬은 공고 API가 담당하고,
다음 학습 추천은 기존 fit API가 담당한다.

## 오류와 빈 상태

### 개인화 피드

- 개인화 요청 실패: 같은 조건의 일반 최신 공고를 한 번 요청하고
  `맞춤 순서를 적용하지 못해 최신 공고를 보여드립니다.`를 한 번만 안내한다.
- 보유 기술과 일치하는 공고가 없음: 탐색 스트림으로 채우고
  `현재 공개 공고에서 일치 항목을 찾지 못했습니다.`를 브리핑에 표시한다.
- 일부 공고에 추출 기술이 없음: 탐색 공고로 취급하며 임의의 기술을 추론하지 않는다.

### 스킬맵

- 새 중심 기술의 관계망 요청 실패: 기존 그래프를 유지하고 패널 안에서 다시 시도한다.
- Canvas 로딩 실패: 현재의 접근 가능한 정적 fallback 노드를 유지한다.
- 필터 결과 없음: 필터 초기화 행동을 함께 제공한다.
- 선택 기술에 근거 공고 없음: `현재 확인 가능한 관련 공고가 없습니다.`라고 표시한다.

## 접근성

- Canvas만으로 정보를 전달하지 않고 현재 보이는 기술을 키보드로 선택할 수 있는 목록을 제공한다.
- 색 외에 크기, 테두리, 점, 텍스트 상태를 함께 사용한다.
- 포커스 링은 즉시 표시하고 3:1 이상 대비를 유지한다.
- 그래프 상태 변경은 짧은 `aria-live` 문장으로 알린다.
- 모바일 하단 내비게이션과 그래프 제어가 겹치지 않도록 safe-area를 포함한다.

## 검증 범위

사용자가 과도한 테스트를 원하지 않았으므로 기능 위험에 직접 대응하는 테스트만 추가한다.

### 백엔드

- C++ 필수 공고가 C++ 비일치 공고보다 먼저 정렬된다.
- 필수, 우대, 분류되지 않음 순서가 지켜진다.
- 4:1 혼합이 페이지 경계에서도 중복·누락 없이 유지된다.
- 별칭과 중복 기술이 canonicalize된다.
- 개인화가 없을 때 기존 공고 순서가 보존된다.
- 그래프 depth 1과 2의 노드 범위가 다르고 한도를 넘지 않는다.

### 웹

- 첫 SSR 요청과 다음 무한 스크롤 요청이 같은 기술 목록을 전달한다.
- C++ 공고 카드에 실제 일치 이유와 C++ 태그가 표시된다.
- 개인화 실패 시 일반 공고 fallback과 안내가 표시된다.
- 추천 점은 상위 3개에만 적용된다.
- 모바일 그래프 조작 모드가 스크롤과 그래프 이동을 명확히 전환한다.

### 브라우저

- 데스크톱: C++ 등록 후 첫 공고 슬롯 5개 중 4개가 C++ 일치인지 확인한다.
- 모바일: 노드 탭, 스크롤 모드, 그래프 조작 모드, 핀치 확대를 확인한다.
- 320, 390, 768, 1440px에서 가로 넘침과 하단 내비게이션 겹침을 확인한다.
- 그래프 요청이 `owned_skills` 없이 공유 캐시 가능한 URL인지 확인한다.

## 범위 밖

- 협업 필터링, 클릭 로그 기반 머신러닝, 사용자 프로파일 벡터
- WebGL 또는 Web Worker 그래프 엔진 전환
- 30개를 넘는 노드를 한 화면에 동시에 렌더링
- 수집되지 않은 기술이나 공고 내용을 추정해 추천 근거로 사용
- 커뮤니티 글의 추천 알고리즘 변경

## 성공 기준

- `C++`만 등록한 사용자의 첫 공고 슬롯 5개 중 가능한 경우 4개가 C++과 일치한다.
- 모든 맞춤 공고 카드에서 추천 이유를 실제 추출 기술로 설명할 수 있다.
- 초기 SSR과 이후 페이지에서 공고 중복·누락이 없다.
- 홈에서 스킬 그래프 네트워크 요청이 사라진다.
- 스킬맵 관계망 URL에 `owned_skills`가 포함되지 않는다.
- 기본 그래프는 데스크톱 12개/18개 선, 모바일 8개/10개 선 예산을 지킨다.
- 사용자는 선택 기술에서 관련 공고 또는 기술 추가 행동으로 한 번에 이동할 수 있다.
