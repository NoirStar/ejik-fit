# 채용 공고 상세 본문 신뢰도 복구 설계

- 상태: 사용자 승인
- 승인일: 2026-07-28
- 선택안: 목록 수집과 상세 본문 수집을 분리하고 품질 게이트를 적용하는 구조
- 대상: 네이버 계열을 포함해 운영에서 본문이 희소한 공고와 기업 로고

## 1. 배경

운영 중인 네이버웹툰 공고 `[네이버웹툰] 프런트엔드 개발자 (글로벌 웹 플랫폼) (경력)`은 공식 상세 페이지에 조직 소개, 담당 업무, 필요 역량, 우대 사항이 모두 있지만 DB에는 목록 API의 분류값을 합친 43자만 저장돼 있다. 따라서 기술 추출기는 입력할 본문이 없어 기술을 한 개도 확정하지 못한다.

같은 공고의 공식 상세 페이지에서 `.detail_wrap .detail_box` 섹션 전체를 정제한 진단 결과는 다음과 같다.

- 정제 본문: 2,651자
- 확인된 기술: React, TypeScript, Next.js, Node.js, Docker, Kubernetes, LLM
- 공식 페이지 구조: 빈 `.detail_text` 뒤의 형제 `div`들에 실제 본문이 이어짐

즉, 기술 추출기의 주된 결함이 아니라 목록 응답을 상세 본문으로 취급한 수집 계약의 결함이다. 네이버웹툰 로고는 32×32 파비콘을 56px 영역에 사용해 화질 보호 로직이 이니셜로 대체하고 있으며, 공식 채용 페이지에는 고해상도 SVG 로고가 별도로 존재한다.

2026-07-28 운영 공개 공고 1,780건을 조사한 결과, 본문 120자 미만이고 설명 이미지도 없는 공고가 최소 14개 기업에서 136건 확인됐다. 현재 공개 수량은 채용 마감과 신규 등록에 따라 달라질 수 있으므로 136은 고정 목표치가 아니라 복구 시작 시점의 결함 기준선이다.

## 2. 목표

1. 공고 목록은 발견과 마감 판단에만 사용하고 기술 추출은 공식 상세 본문을 기준으로 한다.
2. 목록 메타데이터뿐인 공고가 수집 성공으로 저장되는 일을 차단한다.
3. 상세 페이지 일부가 실패해도 기존 정상 본문을 덮어쓰거나 공고를 잘못 마감하지 않는다.
4. 현재 확인된 희소 공고를 공식 원문으로 재수집하고 기술 근거를 다시 계산한다.
5. 네이버웹툰을 포함한 기업 로고는 충분한 해상도의 공식 자산을 사용한다.
6. 이후 같은 결함을 자동으로 발견할 수 있는 운영 품질 감사를 제공한다.

## 3. 비목표

- 공고 제목이나 기업명만 보고 존재하지 않는 기술을 추측하지 않는다.
- 한 개의 범용 CSS 선택자나 브라우저 자동화로 모든 채용 사이트를 처리하지 않는다.
- 공식 원문에 없는 내용을 생성형 모델로 보충하지 않는다.
- 이미지형 공고를 텍스트 길이만으로 불량 처리하지 않는다.
- 외부 채용 사이트의 전체 HTML, 내비게이션, 추적 스크립트를 그대로 저장하거나 노출하지 않는다.

## 4. 선택한 구조

### 4.1 발견과 상세 수집의 분리

각 커넥터는 다음 두 단계를 명시적으로 수행한다.

1. 목록 단계는 `external_id`, 제목, 공식 URL, 고용 형태, 경력, 마감일을 발견한다.
2. 상세 단계는 공식 URL이나 공식 상세 API를 요청해 업무, 자격 요건, 우대 사항, 기술 스택을 파싱한다.

목록 단계의 분류명, 조직명, 키워드는 필터링과 보조 메타데이터로만 사용한다. 상세 수집이 필요한 커넥터에서는 이 값을 `description_text`의 최종값으로 저장하지 않는다.

### 4.2 상세 파서 계약

상세 파서는 다음 계약을 만족해야 한다.

- 목록에서 발견한 `external_id`와 상세 페이지의 공고 식별자가 일치해야 한다.
- 제목이 비어 있거나 다른 공고로 판명되면 실패한다.
- 내비게이션과 공통 푸터를 제외한 공고 본문 섹션만 `description_html`로 만든다.
- `description_text`는 `structured_plain_text`로 정제해 제목과 목록 경계를 보존한다.
- 스크립트, 스타일, 추적 요소와 화면에 보이지 않는 콘텐츠는 제거한다.
- 정제된 본문이 상세 품질 기준을 통과하지 못하면 파싱 성공으로 반환하지 않는다.

네이버 채용 페이지처럼 빈 표준 태그 뒤에 실제 콘텐츠가 형제 요소로 이어지는 경우 특정 하위 태그만 선택하지 않고 검증된 섹션 컨테이너 전체를 정제한다.

### 4.3 상세 품질 게이트

새 공통 품질 판정은 다음 두 형태 중 하나를 정상 상세로 인정한다.

#### 텍스트형 공고

- 공고 본문에서 정규화한 가시 텍스트가 120자 이상이다.
- 목록 단계의 제목·조직·분류값만 이어 붙인 요약과 동일하지 않다.
- 커넥터가 검증한 상세 본문 필드 또는 상세 섹션에서 만들어졌다.

#### 이미지형 공고

- 공식 공고와 동일한 호스트 또는 허용된 공식 자산 호스트의 설명 이미지가 있다.
- 장식 아이콘이나 로고가 아니라 본문 이미지 크기 조건을 통과한다.
- 이미지가 없는 짧은 텍스트만으로는 예외를 허용하지 않는다.

120자는 운영 결함 탐지 기준이다. 특정 공식 API가 구조화된 업무·자격 필드를 제공하면 각 필드 존재 여부도 함께 검사해 메타데이터가 우연히 120자를 넘어서 통과하는 일을 막는다.

### 4.4 실패와 데이터 보존

상세 요청 또는 파싱이 실패한 공고는 다음처럼 처리한다.

- 해당 실행에서 새 희소 본문을 저장하지 않는다.
- 이미 정상 본문이 있는 기존 공고는 그대로 보존한다.
- 목록에는 존재하지만 상세 확인에 실패한 ID는 곧바로 마감 처리하지 않는다.
- 일부 상세만 실패하면 소스 오류를 `partial_detail_failure`로 기록하고 성공한 공고만 갱신한다.
- 공식 404/410으로 삭제가 확인된 경우에만 기존 연속 누락 규칙으로 마감 후보가 된다.
- 모든 상세가 실패한 실행은 소스 성공으로 기록하지 않는다.

이 규칙은 상세 사이트의 일시 장애가 시장 통계와 저장 공고를 대량으로 지우는 일을 막는다.

## 5. 대상 소스와 수집 방식

| 대상 | 현재 문제 | 상세 수집 방식 |
| --- | --- | --- |
| NAVER, Naver Cloud, 네이버웹툰, KREAM, SNOW, NAVER LABS | 네이버 목록 JSON의 분류값만 저장 | 공식 `rcrt/view.do` HTML의 검증된 상세 섹션 파싱 |
| LINE Plus | Gatsby 목록 메타데이터만 저장 | 공식 상세 `page-data.json`의 공고 본문 파싱 |
| 두나무 | 공개 목록 API의 직군·경력만 저장 | 목록 API는 유지하고 공식 `/detail/{id}` 상세 HTML 파싱 |
| CJ OliveNetworks | 목록 JSON만 저장 | 공식 상세 HTML 또는 동일 페이지의 공식 구조화 응답 파싱 |
| 한화시스템, 현대자동차, LG CNS, LG유플러스, 스마일게이트, KT | 기업별 목록 응답만 저장 | 각 공식 상세 API나 페이지 내 구조화 데이터용 전용 파서 추가 |
| 기아 | 브라우저 목록에서 짧은 요약만 저장 | 공식 상세 화면 렌더 결과에서 본문 영역을 파싱하고 기술 직군을 재검증 |

상세 HTML이 서버에서 제공되는 소스는 일반 HTTP 요청을 우선한다. 공식 상세 API나 페이지 데이터가 있으면 브라우저 렌더링보다 이를 우선한다. 브라우저 렌더링은 공개 HTML/API로 본문을 얻을 수 없는 소스에만 제한해 속도와 안정성을 유지한다.

## 6. 기술 추출과 기술 사전

상세 본문 저장 후 기존 근거 기반 기술 추출기를 다시 실행한다. 필수·우대 섹션 제목은 HTML 구조를 유지해 `required`, `preferred`, `unspecified` 분류에 사용한다.

공식 본문에서 반복적으로 확인되지만 현재 기술 사전에 없는 용어는 별도 테스트를 거쳐 추가한다. 이번 기준 공고에서는 Electron과 WebGL을 우선 검토한다. EPUB 같은 파일 형식과 특정 AI 코딩 제품명은 시장에서 학습 가능한 기술로 유용한지 검증한 뒤 추가하며, 단순 문자열 등장만으로 기술 사전을 무제한 확장하지 않는다.

## 7. 기업 로고

네이버웹툰의 32×32 파비콘 매핑을 공식 채용 페이지의 `logo_2025.svg`로 교체한다.

- 로고 프록시는 공식 호스트만 허용한다.
- SVG 응답의 콘텐츠 유형과 캐시 헤더를 검증한다.
- 표시 크기와 DPR 기준을 통과해 `CompanyMark`가 이니셜로 대체하지 않는지 테스트한다.
- 공식 고해상도 자산을 찾지 못한 기업은 저품질 이미지를 억지로 확대하지 않고 현재 이니셜 대체를 유지한다.

## 8. 사용자 화면의 안전한 상태

재수집 전에 남아 있거나 일시적인 상세 실패가 발생한 희소 공고를 긴 원문처럼 오해하게 하지 않는다.

- 텍스트 120자 미만이고 설명 이미지가 없으면 `공고 원문` 제목 아래에 메타데이터를 원문처럼 표시하지 않는다.
- 대신 `상세 내용 수집을 점검 중입니다. 지원 요건은 공식 공고에서 확인해 주세요.`와 공식 공고 링크를 제공한다.
- 정상 본문 또는 설명 이미지가 있으면 기존 상세 표시를 유지한다.

이 화면 처리는 데이터 복구의 대체 수단이 아니라 잘못된 신뢰를 막는 임시 안전장치다.

## 9. 운영 품질 감사와 복구

### 9.1 수집 시 예방

상세 필수 커넥터는 품질 게이트를 통과한 공고만 저장한다. 실패 개수와 예시 ID를 크롤 결과와 GitHub 작업 요약에 남긴다.

### 9.2 기존 데이터 감사

운영 감사 명령은 공개 공고를 소스·기업별로 집계하고 다음 값을 출력한다.

- 공개 공고 수
- 정상 텍스트형 공고 수
- 정상 이미지형 공고 수
- 희소 공고 수와 대표 공고 ID
- 본문이 있는데 확정 기술이 0개인 공고 수

감사 결과는 비밀값이나 공고 전체 본문을 로그에 출력하지 않는다.

### 9.3 재수집 순서

1. 새 상세 파서와 품질 게이트를 배포한다.
2. 네이버 계열, LINE Plus, 두나무, CJ를 먼저 재수집한다.
3. 기업별 SPA/API 소스와 기아를 재수집한다.
4. 각 재수집 직후 기술 근거와 검색 인덱스를 갱신한다.
5. 운영 감사를 다시 실행해 시작 시점의 136건을 각각 정상 본문, 공식 이미지형, 마감/삭제, 비기술 공고로 설명한다.

단순히 희소 공고 숫자를 숨기는 것으로 완료하지 않는다. 현재도 공개 중인 기술 공고는 공식 본문이 저장되고 기술 추출 근거가 생성돼야 한다.

## 10. 성능과 안정성

- 목록 요청은 현재처럼 한 번만 수행하고 상세 요청만 공고별로 추가한다.
- 사이트별 요청 지연, 재시도, 타임아웃을 유지해 공식 사이트에 과도한 요청을 보내지 않는다.
- 정적 JSON과 서버 HTML을 브라우저 렌더링보다 우선한다.
- 같은 실행에서 중복 상세 URL은 한 번만 요청한다.
- 네트워크 수집과 DB 저장을 분리해 DB 세션을 비동기 병렬 작업에 공유하지 않는다.
- 병렬 요청이 안전한 공식 API만 작은 동시성 상한을 사용하고, 나머지는 기존 순차 수집을 유지한다.
- 상세 실패가 목록 전체 재요청이나 무한 재시도를 유발하지 않게 한다.
- 웹 상세 페이지는 이미 저장된 정제 본문만 렌더하므로 사용자 요청 시 외부 채용 사이트를 호출하지 않는다.

## 11. 테스트 전략

모든 구현은 실패하는 테스트를 먼저 추가한다.

### 커넥터 단위 테스트

- 실제 응답 형태를 축소한 고정 fixture로 제목, ID, 섹션, 본문 길이를 검증한다.
- 네이버의 빈 `.detail_text`와 형제 `div` 구조를 재현한다.
- HTML 태그와 내비게이션 문구가 `description_text`에 노출되지 않는지 확인한다.
- 필수·우대 섹션의 기술 근거 분류를 확인한다.
- 120자 미만의 목록 메타데이터와 잘못된 상세 ID가 실패하는지 확인한다.

### 크롤러 통합 테스트

- 목록 발견 뒤 공식 상세 URL을 요청하는지 확인한다.
- 일부 상세 실패 시 정상 공고만 갱신하고 기존 정상 공고를 보존하는지 확인한다.
- 일부 상세 실패 실행이 누락 공고를 마감하지 않는지 확인한다.
- 공식 404/410과 일시 오류를 구분하는지 확인한다.
- 재수집 시 기존 기술 근거가 새 본문에 맞게 교체되는지 확인한다.

### 웹과 로고 테스트

- 희소 공고는 오해를 부르는 `공고 원문` 대신 점검 안내와 공식 링크를 표시한다.
- 정상 텍스트형과 이미지형 공고는 기존 상세 경험을 유지한다.
- 네이버웹툰 공식 SVG가 프록시되고 이니셜 대신 표시된다.

### 회귀 검증

- 전체 백엔드 테스트
- 전체 웹 테스트와 TypeScript 검사
- 프로덕션 웹 빌드
- 실제 배포 API와 공식 URL을 사용한 공개 smoke 검사

## 12. 완료 기준

1. 기준 네이버웹툰 공고의 운영 API 본문이 2,000자 이상이고 React, TypeScript, Next.js, Node.js, Docker, Kubernetes가 근거와 함께 반환된다.
2. 기준 공고에서 HTML 태그가 일반 텍스트로 노출되지 않는다.
3. 네이버웹툰 상세와 카드에서 공식 SVG 로고가 선명하게 표시된다.
4. 시작 시점의 희소 공고 136건이 재감사에서 정상 본문, 공식 이미지형, 마감/삭제, 비기술 공고 중 하나로 모두 설명된다.
5. 공개 중인 대상 기술 공고는 목록 메타데이터만 저장된 상태로 남지 않는다.
6. 새 상세 실패가 기존 정상 데이터나 공고 상태를 훼손하지 않는다.
7. 전체 테스트, 타입 검사, 프로덕션 빌드, 배포 후 smoke 검사가 통과한다.

## 13. 배포와 되돌리기

배포는 파서·품질 게이트, 웹 안전 상태, 재수집 순서로 진행한다. 재수집 전에 배포된 코드는 기존 DB 스키마와 호환돼야 한다.

문제가 발생하면 새 상세 수집 분기만 비활성화하고 기존 정상 본문은 유지한다. 품질 게이트가 실패한 짧은 본문은 정상 데이터를 덮어쓰지 않으므로 데이터 롤백 없이 커넥터 코드를 되돌릴 수 있어야 한다.
